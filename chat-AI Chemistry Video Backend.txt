
# AI Agent Implementation Specification  
## Chemistry Educational Video Generation Backend

This document is the authoritative requirement and implementation plan for building the backend service.

You are an AI agent implementing this system. Read the entire document before writing code. Follow the phases in order. Do not skip validation, tests, or failure handling. The goal is not only to produce one working video. The goal is to build a reliable backend pipeline that consistently produces short educational chemistry videos.

---

## 1. Product Summary

Build a backend service that accepts a request for a short educational chemistry video, processes the request asynchronously, and returns a completed video artifact.

The product must feel like a backend video-generation job service:

1. A client submits a concept request.
2. The backend creates a job.
3. The job moves through generation stages.
4. The client can poll job status.
5. When complete, the client can retrieve the video artifact.

This is a backend-only service. Do not build a frontend. Demonstrate using `curl`, automated tests, or a simple script.

---

## 2. Primary Goals

The implementation must achieve:

1. A FastAPI backend.
2. An endpoint to request a chemistry explanation video.
3. Asynchronous job processing.
4. An endpoint to list jobs.
5. A visible status and stage for each job.
6. A way to retrieve the completed video artifact.
7. A generated MP4 video with visual content and audio.
8. Clear backend boundaries:
   - API layer
   - job state
   - generation logic
   - persistence
   - artifact storage
9. Reliable generation despite non-determinism.
10. Support for three required chemistry queries.
11. Clear extensibility for future STEM concepts.

---

## 3. Required Learner Queries

The service must support these three queries end-to-end:

1. `How does the pH scale work?`
2. `Why do atoms form covalent bonds?`
3. `What is the difference between ionic and covalent bonding?`

The service does not need to support arbitrary chemistry topics in this prototype.

However, the architecture must make it clear how future concepts can be added through configuration or content packs.

---

## 4. Core Design Philosophy

The agent must follow this design philosophy:

> Use deterministic, template-based video generation as the default path. Use AI providers only behind validated interfaces. Never trust generated output without validation.

Do not build the system around fully open-ended generative video models as the primary renderer. That approach is too unstable for this challenge.

Instead:

- Use curated scripts for the three required concepts.
- Use structured scene templates.
- Use deterministic rendering where possible.
- Validate scripts, audio, and final video artifacts.
- Use retries and fallbacks only where they improve reliability.
- Fail with clear error states.

## 5. Technology Requirements

Use the following stack unless there is a strong technical reason not to.

### Language

- Python 3.11+

### Backend framework

- FastAPI
- Uvicorn
- Pydantic v2
- Pydantic Settings

### Persistence

Prototype:

- In-memory job repository
- Local filesystem artifact store

Production-ready evolution:

- SQLite or PostgreSQL for jobs
- S3-compatible object storage for artifacts

### Video generation

Recommended deterministic renderer:

- Pillow for frame generation
- FFmpeg for encoding
- Optional MoviePy or Manim if easier, but FFmpeg must be available

System dependencies:

- `ffmpeg`
- `ffprobe`

Optional audio dependencies:

- `espeak-ng`
- or cached pre-generated narration files
- or a TTS provider behind an adapter

### Testing

- pytest
- pytest-asyncio
- httpx
- FastAPI TestClient or ASGITransport

### Code quality

- type hints everywhere
- ruff or equivalent linter
- mypy or equivalent type checker if practical
- modular code, no monolithic files

### 9.2 Create video job

```http
POST /v1/video-jobs
```

Request body:

```json
{
  "query": "How does the pH scale work?"
}
```

Optional fields:

```json
{
  "query": "How does the pH scale work?",
  "style": "short_explainer",
  "callback_url": "https://example.com/callback"
}
```

Validation rules:

- `query` is required.
- `query` must be between 4 and 300 characters.
- `callback_url`, if present, must be a valid HTTP or HTTPS URL.
- If `Idempotency-Key` header is provided, the service should return the same job for the same key and query instead of creating a duplicate job.

Success response:

```http
202 Accepted
```

```json
{
  "job_id": "8f1e5c6e-3c5f-4d0b-a5b2-2b5a3f9d0a11",
```

## 10. Job State Machine

The job must expose both high-level status and detailed stage.

### High-level status values

```text
queued
running
completed
failed
```

Optional:

```text
canceled
```

### Detailed stage values

```text
queued
concept_resolution
script_selection
script_validation
storyboard_generation
narration_generation
scene_rendering
video_composition
artifact_validation
completed
failed
```

### Valid transitions

```text
queued -> concept_resolution
concept_resolution -> script_selection
script_selection -> script_validation
script_validation -> storyboard_generation
storyboard_generation -> narration_generation
narration_generation -> scene_rendering
scene_rendering -> video_composition
video_composition -> artifact_validation
artifact_validation -> completed
```

Any stage may transition to:

```text
failed
```

Optional cancellation:

```text
queued -> canceled
running -> canceled
```

Do not allow invalid transitions.

## 13. Concept Registry

Implement a concept registry.

The registry must resolve normalized queries to concept IDs.

Normalization rules:

1. Trim whitespace.
2. Convert to lowercase.
3. Remove punctuation.
4. Collapse multiple spaces.
5. Remove trailing question mark.
6. Match against alias list.

Example:

```text
"How does the pH scale work?"
```

becomes:

```text
how does the ph scale work
```

Required concept IDs:

```text
ph-scale
covalent-bonding
ionic-vs-covalent
```

Required aliases:

```json
{
  "ph-scale": [
    "how does the ph scale work",
    "how does the ph scale work?",
    "ph scale",
    "explain the ph scale",
    "what is the ph scale"
  ],
  "covalent-bonding": [
    "why do atoms form covalent bonds",
    "why do atoms form covalent bonds?",
    "covalent bonding",
    "why covalent bonds form",
    "explain covalent bonding"
  ],
  "ionic-vs-covalent": [
    "what is the difference between ionic and covalent bonding",
    "what is the difference between ionic and covalent bonding?",
    "ionic vs covalent",
    "difference between ionic and covalent bonding",
    "compare ionic and covalent bonds"
  ]
}
```

If no concept is matched, reject the request with:

```text
UNSUPPORTED_CONCEPT
```

## 18. Script Source Policy

Default policy:

```text
SCRIPT_SOURCE=canonical
```

This means:

- Use curated canonical scripts.
- Do not call an LLM by default.
- This gives deterministic, reliable output.

Optional policy:

```text
SCRIPT_SOURCE=canonical_with_llm_fallback
```

If enabled:

1. Try LLM script generation.
2. Validate output.
3. If invalid, retry once with validation errors.
4. If still invalid, fall back to canonical script.
5. Record which script source was used.

LLM output must be JSON and must match the script schema.

Do not use raw freeform LLM output directly.

## 19. Script Schema

Every script must conform to this schema:

```json
{
  "concept_id": "ph-scale",
  "title": "How the pH Scale Works",
  "summary": "The pH scale shows whether a solution is acidic, neutral, or basic.",
  "target_duration_seconds": 60,
  "scenes": [
    {
      "scene_id": 1,
      "layout": "title",
      "narration": "string",
      "visual_description": "string",
      "on_screen_labels": ["string"]
    }
  ]
}
```

Validation rules:

1. `concept_id` must match the resolved concept.
2. `title` must be non-empty.
3. `summary` must be non-empty.
4. `scenes` must contain 4 to 10 scenes.
5. Each scene must have non-empty narration.
6. Each scene must have non-empty visual description.
7. Each scene must have at least one on-screen label.
8. Required concept terms must appear in the combined narration and labels.
9. Estimated narration duration must fit target duration.
10. No scene may exceed 20 seconds unless necessary.
11. No unsafe or irrelevant chemistry claims.

## 21. Audio Generation Requirements

The final video must include audio.

Preferred audio strategy:

1. Use cached pre-generated narration files if available.
2. If not available, use local TTS such as `espeak-ng`.
3. If a remote TTS provider is configured, use it behind an adapter.
4. If no audio provider is available and `ALLOW_PLACEHOLDER_AUDIO=false`, fail the job.
5. If `ALLOW_PLACEHOLDER_AUDIO=true`, generate a placeholder audio track, but mark metadata clearly as placeholder and include subtitles.

Narration provider interface:

```python
class NarrationProvider:
    def generate(
        self,
        text: str,
        voice: str | None = None,
    ) -> AudioResult:
        ...
```

Audio result must include:

```python
class AudioResult(BaseModel):
    file_path: Path
    duration_seconds: float
    provider: str
    is_placeholder: bool
    sample_rate: int | None
    checksum_sha256: str
```

Audio validation:

1. File exists.
2. File size is greater than zero.
3. Duration is greater than 0.3 seconds.
4. Audio can be parsed by FFmpeg.
5. Audio sample rate is valid.
6. Audio is not completely silent unless placeholder mode is enabled.

Audio must be cached by:

```text
sha256(text + voice + provider)
```

This avoids repeated generation and improves consistency.

## 23. Rendering Implementation Strategy

The recommended implementation is:

1. For each scene, generate image frames using Pillow.
2. Create audio for each scene.
3. Encode each scene into a temporary MP4 using FFmpeg.
4. Concatenate scene videos into final MP4.
5. Generate subtitles from scene timing.
6. Generate thumbnail from a representative frame.
7. Validate final MP4.

Example FFmpeg command pattern for a scene:

```bash
ffmpeg -y \
  -framerate 30 \
  -i scene_frames/%04d.png \
  -i scene_audio.wav \
  -c:v libx264 \
  -pix_fmt yuv420p \
  -c:a aac \
  -shortest scene.mp4
```

Example concat file:

```text
file 'scene_01.mp4'
file 'scene_02.mp4'
file 'scene_03.mp4'
```

Example concat command:

```bash
ffmpeg -y -f concat -safe 0 -i concat.txt -c copy final.mp4
```

If codec parameters differ, re-encode instead of using `-c copy`.

4. Video stream exists.
5. Audio stream exists.

7. Resolution is correct.
8. Video codec is H.264 or compatible.
9. Audio codec is AAC or compatible.
10. Subtitles file exists.
11. Thumbnail exists.
12. Metadata file exists and is valid JSON.

Failure code:

```text
VIDEO_VALIDATION_FAILED
```

## 29. Retry and Fallback Policy

Retries must be limited.

Do not retry indefinitely.

### Script generation

If using canonical script:

```text
No retry needed.
```

If using LLM:

```text
max_attempts: 2
fallback: canonical script
```

### Audio generation

```text
max_attempts: 2
fallback: cached narration if available
if no fallback: fail job
```

### Rendering

```text
max_attempts: 2
fallback: none
if second attempt fails: fail job
```

### Artifact validation

```text
If validation fails after render:
  retry rendering once
if validation fails again:
  fail job
```

### Timeouts

Each job must have a timeout.

Default:

```text
JOB_TIMEOUT_SECONDS=900
```

If timeout is exceeded:

```text
status = failed
stage = last known stage
error.code = JOB_TIMEOUT
```

## 32. Worker Requirements

The worker must process jobs asynchronously.

Prototype implementation:

- FastAPI startup creates a worker task.
- Jobs are placed into an in-process queue.
- Worker consumes queue.
- Blocking rendering runs in a thread or executor.

Production evolution:

- Redis or SQS queue
- separate worker process
- retry queue
- dead-letter queue
- concurrency controls

The worker must update job stage and progress as it advances.

The worker must catch exceptions and mark the job failed with a meaningful error.

The worker must not crash the API process.

- do not start more than configured concurrent jobs

## 43. Docker Requirements

Provide a Dockerfile.

Minimum Dockerfile behavior:

1. Use Python 3.11 slim image.
2. Install FFmpeg.
3. Install fonts.
4. Install Python dependencies.
5. Copy app code.
6. Run Uvicorn.

Example:

```dockerfile
FROM python:3.11-slim

ENV PYTHONUNBUFFERED=1

RUN apt-get update && apt-get install -y \
    ffmpeg \
    fonts-dejavu \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY pyproject.toml ./
COPY app ./app
COPY assets ./assets

RUN pip install --no-cache-dir .

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```yaml
services:

    ports:
      - "8000:8000"

    build: .

```

## 48. Content Accuracy Rules

```text
Ionic bonds always form between metals and nonmetals.
```
